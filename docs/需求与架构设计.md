# 种子搜索 —— 需求与架构设计

> 版本 1.0.0 ｜ 目标运行环境：Node.js ≥ 20（开发验证于 Node 26.8.1 / Windows 11）
> 交付形态：命令行工具 + 本地 Web UI + JSON API，**零运行时依赖**

---

## 1. 背景与目标

「种子搜索」要解决的问题很具体：公开的磁力/BT 站点各自为政，接口格式五花八门、可用性随时波动，
用户想找一个资源往往要在好几个站点之间来回切换、还要忍受弹窗与反爬。

本项目把多个公开索引站聚合成**一个本地入口**，做到：

| 目标 | 具体标准 |
| --- | --- |
| 一处搜索，多源聚合 | 一次查询并发打到所有启用的数据源，结果合并去重 |
| 结果可解释 | 每条结果标明来源，每个源的成败/耗时/条数都如实展示，失败不隐藏 |
| 零依赖、开箱即用 | 不需要 `npm install`，不需要构建步骤，不需要 Python/Go 运行时 |
| 三种用法 | CLI（可管道、可脚本化）、Web UI（可视化浏览）、JSON API（可被其它程序调用） |
| 可验证 | 离线单元测试 + 实网冒烟测试，站点改版时能立刻发现 |
| 合规 | 只聚合公开索引信息，不托管、不缓存、不分发任何受版权保护的内容 |

**非目标**（明确不做）：不做下载器、不做 Tracker、不做私有站点（PT）登录、不做内容审核/过滤策略的裁决。

## 3. 数据源调研结论（实测）

> 以下结论均为**实测**（含响应格式、字段名、坑），不是文档推测。夹具保存在 `test/fixtures/`。

| 源 | 接口 | 格式 | 关键字段 | 限制与坑 |
| --- | --- | --- | --- | --- |
| The Pirate Bay（apibay） | `GET apibay.org/q.php?q=` | JSON 数组 | `name/info_hash/size/seeders/leechers/added/category` | 一次最多 100 条、无分页；无结果时返回**占位条目**（`id=0`、`name="No results returned"`）必须过滤；`size` 是原始字节字符串 |
| Nyaa | `GET nyaa.si/?page=rss&q=&c=0_0&f=0` | RSS + `nyaa:` 命名空间 | `nyaa:seeders/leechers/infoHash/size/category` | 必须走 RSS（HTML 有反爬）；`<link>` 是 .torrent 下载地址，详情页在 `<guid>` |
| BitSearch | `GET bitsearch.to/api/v1/search?q=&limit=&sort=` | JSON | `infohash/title/size/seeders/leechers/updatedAt/category` | 详情页用 **mongo id** 而非 infohash；`limit` 上限 100；与 solidtorrents 同后端（不重复接入）；分类表来自该站搜索页：1 其他 / 2 电影 / 3 剧集 / 4 动漫 / 5 软件 / 6 游戏 / 7 音乐 / 8 有声书 / 9 电子书课程 / **10 XXX**；**该站的 sort 会换掉整批结果（见 5.14），本项目固定用 `sort=seeders` 抓取** |
| Mikan Project（蜜柑计划） | `GET mikanani.me/RSS/Search?searchstr=` | RSS | `torrent/contentLength/pubDate`、`enclosure` | 无做种数；`pubDate` **无时区**（按 UTC+8 解释）；Episode 路径的 40 位 hex 经验证**就是 info hash** |
| 动漫花园（dmhy） | `GET share.dmhy.org/topics/rss/rss.xml?keyword=` | RSS | `enclosure` 里的磁力、`category` | 磁力的 btih 是 **Base32**（32 字符），必须转 40 位 hex 才能跨站去重；无体积/做种数；单次最多 500 条（响应可达 2 MB） |
| Academic Torrents | `GET academictorrents.com/database.xml` | RSS（全量库） | `title/infohash/size/category` | **没有搜索接口**，官方要求别爬 browse 页；全量库约 3 MB（实测 2870 条），每天更新一次 → 缓存到磁盘后本地检索 |

**被排除的源及原因**：`1337x`/`bt4g`（Cloudflare 403）、`knaben`（连接超时）、`solidtorrents`（与 BitSearch 同后端，重复）。

**结论**：公开源里最稳定的形态是 **RSS + JSON 接口**，而不是 HTML 抓取。
因此架构把「RSS 解析器」当作一等公民（`src/xml.mjs` + `src/rss.mjs`），HTML 抓取一律不碰。

## 4. 总体架构

```
┌──────────────────────────────────────────────────────────────────────┐
│  入口层                                                              │
│   bin/magnet-search.mjs (CLI)      src/server.mjs (HTTP API + Web)   │
│        │                                   │                         │
│        └───────────────┬───────────────────┘                         │
│                        ▼                                             │
│  聚合层  src/aggregate.mjs                                           │
│   并发扇出 → 容错收集 → 跨源去重 → 相关度评分 → 排序 → 分页          │
│                        │                                             │
│         ┌──────────────┼──────────────┬──────────────┐               │
│         ▼              ▼              ▼              ▼               │
│  数据源适配器  src/sources/*.mjs（统一契约：search(query, ctx)）      │
│   apibay  nyaa  bitsearch  mikan  dmhy  academic  demo               │
│                        │                                             │
│  基础设施层            ▼                                             │
│   src/http.mjs（直连 fetch / 自建 CONNECT 代理隧道、超时、重试、限流）│
│   src/xml.mjs + src/rss.mjs（极简 XML 解析）                         │
│   src/cache.mjs（磁盘缓存，原子写入）                                │
│   src/magnet.mjs（Base32↔hex、磁力构造/解析）                        │
│   src/models.mjs（统一结果模型、去重键、中文分词）                   │
│   src/size.mjs（体积/时间归一化）  src/format.mjs（终端表格）        │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.1 数据流

```
用户输入关键词
  → resolveSources() 决定查询哪些源
  → Promise.all 并发：每个源独立 AbortSignal（超时只影响自己）
  → 每个适配器：HTTP 请求 → 解析（JSON/RSS）→ makeResult() 规范化
  → 收集成功结果 + 记录每源状态 {ok, count, tookMs, error}
  → mergeResults()：按 info hash（无 hash 则标题+体积）合并
  → scoreResult()：相关度 55% + 做种热度 30% + 新鲜度 15%（+跨源 5%）
  → sortResults() → 分页切片
  → 返回 {results, sources[], total, tookMs, ...}
```

### 4.2 统一结果模型（`TorrentResult`）

| 字段 | 说明 |
| --- | --- |
| `id` | `<source>:<infoHash>`；无 hash 时用「标题+体积」的 SHA1 短哈希 |
| `title` | 标题（去多余空白） |
| `infoHash` | 小写 40 位 hex；非法/缺失为 `null` |
| `magnet` | 磁力链接；有 hash 无磁力时本地构造 |
| `size` / `sizeText` | 字节数 / 人类可读（1024 进制） |
| `seeders` / `leechers` | 做种数 / 下载数；**站点不提供时为 `null`，不编造 0** |
| `category` | 各站原始分类（apibay 做了 TPB 顶级分类中文化） |
| `publishedAt` | ISO 8601；无法解析为 `null` |
| `detailsUrl` / `torrentUrl` | 详情页 / .torrent 地址 |
| `score` / `sources` | 聚合阶段补充：相关度评分 / 合并后的全部来源 |

## 5. 关键设计决策

### 5.1 为什么选 Node.js 而不是 Python
本机没有可用的 Python（只有 Microsoft Store 的占位符 `python.exe`），而 Node 26 已就绪；
且 Node 内置 `fetch`、`http`、`zlib`、`node:test`、`zstd`，**零依赖**目标更容易达成。
代价：Node 的内置 `fetch` 只在启动时读 `NODE_USE_ENV_PROXY`（运行时改 `process.env` 无效），
所以代理路径必须自己实现（见 5.4）。

### 5.2 为什么优先 RSS/JSON，不做 HTML 抓取
实测发现 Cloudflare 会拦下 `1337x`、`bt4g` 等 HTML 站点，而 RSS/JSON 接口稳定得多，
且字段更全（RSS 里连做种数都有）。抓 HTML 需要浏览器指纹/JS 渲染，违背零依赖目标。
**取舍**：宁可少接几个源，也不引入脆弱且高维护成本的抓取逻辑。

### 5.3 去重以 info hash 为准（Base32 必须先归一化）
同一个种子在不同站的标题常常不同（字幕组后缀、分辨率写法），但 info hash 相同。
dmhy 用 Base32、其余站用 hex，若不归一化，同一个种子会被当成两条。
实测验证：搜「进击的巨人」时同一资源被合并为 `dmhy+mikan` 一条。
无 hash 时才退化为「归一化标题 + 体积」匹配。

### 5.4 代理：自己实现 CONNECT 隧道
需求是「`--proxy` 参数随时生效」，而 Node 的内置 `fetch` 只在进程启动时读代理环境变量。
因此 `src/http.mjs` 提供两条路径：
- **直连**：用内置 `fetch`（自动重定向、gzip/br 解压、连接池）；
- **代理**：用 `node:http` 发 `CONNECT` 建隧道 → `node:tls` 做 TLS → 在隧道上发请求，
  自己处理重定向、`content-encoding` 解压（gzip/deflate/br/zstd）、大小上限。
另外支持 `--proxy auto`：依次读 `HTTPS_PROXY/HTTP_PROXY`，Windows 上再回退读注册表
`Internet Settings\ProxyServer`（含 `http=...;https=...` 这种分协议格式）。

### 5.5 容错：把失败当数据，而不是异常
每源独立 `AbortSignal.timeout()`，用 `Promise.all` 收集（内部各自 try/catch），
失败信息（超时/HTTP 403/解析失败/未知源）随结果一起返回。
CLI 会打印 `数据源：apibay ✓ 100 条 420ms · nyaa ✗ 超时 (8000ms)`，Web UI 用红色徽章 + 悬停全文。
**理由**：聚合搜索里「某个源挂了」是用户需要知道的信息，静默吞掉只会让人误以为没有资源。

### 5.6 排序：相关度优先，而不是做种数优先
纯按做种数排会让搜「进击的巨人」时冒出高做种数的无关资源。评分公式：

```
score = 0.55 × 相关度(标题命中比例，全词命中额外 +0.15)
      + 0.30 × min(1, log10(seeders+1)/3)        // 1000 做种 ≈ 满分
      + 0.15 × 新鲜度(1 - 天数/365，下限 0)
      + 0.05 × (跨源命中加成)
```

### 5.7 中文检索
中文没有空格，`tokenize()` 对中文块同时产出「整块」与「单字」两种 token：
整块命中给高相关度，单字命中提高召回（用于本地索引检索与相关性打分）。
终端表格用 East Asian Width 计算显示宽度，避免中英混排错位。

### 5.8 缓存策略
只有 Academic Torrents 需要缓存（无搜索接口，全量库 3 MB、每天更新）：
`DiskCache.getOrFetch()` 带 TTL（12 小时）+ 原子写入（临时文件 + rename），
解析结果按「长度 + SHA1」签名在内存中复用，避免每次搜索重复解析 3 MB XML。
缓存目录：`TORRENT_SEARCH_CACHE` 环境变量，默认 `%LOCALAPPDATA%\torrent-search\cache`（Windows）
或 `~/.cache/torrent-search`。

### 5.9 安全
- 服务默认只监听 `127.0.0.1`，不对外暴露；
- 静态资源做了目录穿越防护（解析后的绝对路径必须仍在 `web/` 内），并有测试覆盖 `/..%2Fpackage.json` → 403；
- Web UI 全部使用 `textContent`/转义，不使用 `innerHTML` 拼接外部数据（有 XSS 载荷实测，并由 `npm run lint` 持续强制）；
- 输入长度/数量有上限：关键词 ≤ 200 字符、排除关键词 ≤ 20 个，超限返回 400。

### 5.10 过滤与安全过滤
过滤在**合并去重之后、评分排序之前**执行，因此 `total` 是过滤后的条数，同时返回 `totalBeforeFilter` 让界面能提示「已过滤 N 条」——
这一点很重要：用户看到"没有结果"时需要知道是**真的没有**，还是**被自己的过滤条件筛掉了**。

| 过滤项 | 规则 | 取舍 |
| --- | --- | --- |
| `minSeeders` | `seeders >= N`；**做种数未知（null）的结果一律过滤掉** | 未知不能当作"有做种"，否则这个过滤形同虚设 |
| `exclude` | ASCII 关键词按**词首边界**匹配、中文按子串匹配 | 避免 `ts` 误伤 `shorts`，同时 `cam` 仍能命中 `camrip` |
| `safe` | 只依据站点自己的分类标注（apibay 5xx、BitSearch 10） | **不猜标题关键词**，避免误杀正常资源；非成人站点永不标记 |

### 5.11 结果缓存
服务端默认缓存 60 秒（`cacheTtlMs`，进程内 LRU，最多 64 条）。三个关键设计：
1. **缓存的是"每源原始结果"，不是最终响应**：过滤、评分、排序、分页每次请求都重新计算，
   所以过滤条件永远即时生效，不会出现"缓存把过滤结果也缓存住"的怪象；
2. **缓存键包含每源抓取条数**：翻页时每源抓取量会变（`limitPerSource` 随页码增长），内容不能混用；
3. **`noCache=1` 只跳过读取、仍然写入**：界面的「重新抓取」按钮因此能刷新缓存而不只是绕过它。

缓存默认**只在服务端开启**：CLI 是一次性进程，缓存没有意义，所以库层默认 `cacheTtlMs: 0`。

### 5.12 排序方向
`sort` 有五个维度、`order` 有 `desc/asc` 两个方向。实现上用「一份降序比较器 + 整体取反」而不是写 10 个分支；
日期缺失的结果统一按「最旧」处理（`timeOf()`），因为 `NaN` 参与比较会让排序结果不可预测。
排序维度会透传给支持排序的源（BitSearch 映射为 `created` 等），所以排序是**全量结果级**的，不是当前页内的重排。

### 5.13 分类体系
各站分类编号含义完全不同，必须各站独立映射（`src/categories.mjs`），并且**未知编号原样返回而不是猜成"其他"**——
让用户看到站点真实给的值，比给一个编造的归类更诚实。

### 5.14 候选池 vs 排序：一个实测出来的坑
大多数站点「一次查询只返回有限条数」（BitSearch/apibay 上限 100，dmhy 上限 500）。
如果把这个上限内的**候选池**交给站点自己的排序参数决定，那么"排序"就不只是重排，而是**换了一批结果**。
实测 BitSearch 对 `ubuntu` 的 100 条候选（`limit=50` 时的做种数统计）：

| 站点排序参数 | 做种数中位数 | 做种数 ≥ 100 的条数 |
| --- | --- | --- |
| `seeders` | 57 | 8 |
| `relevance` | 51 | 8 |
| `leechers` | 44 | 8 |
| `size` | **1** | **0** |

结论：如果按用户选择的维度透传给站点，`--sort size` 会返回"最大的死种"（中位数 1 个做种），
再叠加 `--min-seeders 20` 就直接空结果——用户会以为"没有资源"，其实是候选池被选歪了。

因此本项目采用：**候选池固定按"质量"取（BitSearch 用 `seeders`），五个维度的排序全部在本地对候选池做**。
好处是语义稳定（排序只影响顺序，不影响命中集合），并且与 `minSeeders`/`exclude`/`safe` 等过滤条件不冲突。
代价是"找某个维度上的极端值"不如站点原生排序彻底——对搜索工具而言这个取舍是划算的。

> 这个坑同时暴露了一个缓存设计问题：缓存键最初漏了 `sort`，导致不同排序的请求会复用对方那批候选。
> 现在键为 `关键词|源集合|每源抓取条数|排序`，并有一条专门的回归测试（`test/filters.test.mjs`）。

### 5.15 下载：一个零依赖的最小 BT 引擎

「搜到就能下」是搜索工具的自然延伸。选择自己实现（而不是依赖 aria2/qBittorrent）是为了守住
**零运行时依赖**这条底线——用户 clone 下来就能跑，不需要装任何东西。

**协议子集**（`src/bt/`）：

| 模块 | 职责 | 依据 |
| --- | --- | --- |
| `bencode.mjs` | 编解码、info hash 计算 | BEP 3。字节串一律用 **latin1 字符串**表示：字节 ↔ 字符双射，重编码字节级一致（这是校验 info hash 的前提）；UTF-8 文本用 `toUtf8()` 显式转换 |
| `tracker.mjs` | HTTP(S) announce + UDP announce | BEP 3/23（紧凑 peer 列表）+ BEP 15（UDP）。`info_hash` 是二进制，必须按字节百分号编码（非保留字节原样、其余 %XX），不能用 `encodeURIComponent` |
| `peer.mjs` | Peer 连接：握手、interested/unchoke、bitfield、request/piece | BEP 3。握手长度是 **68** 字节（1+19+8+20+20），写错会截断 peer_id 并让消息流整体错位（本项目真实踩过）；扩展握手 + `ut_metadata` 走 BEP 10/9 |
| `torrent.mjs` | info 字典 → 分片/文件布局；**恶意路径清洗** | 多文件种子的路径来自种子本身，必须先剔除 `.`/`..`/盘符段再清洗（顺序错了 `..` 会变成 `_`，语义被悄悄改掉） |
| `storage.mjs` | 按偏移写盘、读取已有分片 | 目录穿越防护（`assertInside`）；Windows 对 `'a+'` 句柄 `ftruncate` 报 EPERM → 用 `'r+'`/`'w+'`；预分配失败不影响正确性 |
| `dht.mjs` | DHT（BEP 5）：KRPC 查询、紧凑节点编解码、XOR 距离、get_peers 迭代查找 | BEP 5。只做下载侧需要的 `get_peers`；**不实现 announce_peer/PEX**（纯下载方）；UDP 无法经 HTTP 代理，只能当 tracker 的回退通路 |
| `engine.mjs` | 调度：announce →（回退 DHT）→ 拉元数据 → 分片下载 → 校验 → 落盘 | 每 60 秒重 announce 补充 peer；分片校验失败即重试并换 peer；连续 40 次失败才放弃 |

**明确不做的事（以及给用户的后果）**：
- **announce_peer（BEP 5）与 PEX**：不向 DHT 声明资源。我们是纯下载方，声明自己"有种子"毫无意义且会暴露来源。
- 上传/做种、监听入站端口：纯下载客户端。
- 加密传输（MSE）、uTP：走标准 TCP。

**找 peer 的顺序**（DHT 是最后一道回退）：
1. 磁力自带的 tracker；
2. 补充的公共 tracker（默认开启，`--no-extra-trackers` / `useDefaultTrackers: false` 关闭）；
3. **DHT 迭代查找**（`useDht`，默认开启）——仅当上面两步都没拿到 peer 时才走。
   分片下载阶段 peer 用尽时也会补一次 DHT（一轮下载只补一次，避免反复 UDP 探测拖慢速度）。

> DHT 是 UDP，**无法经过 HTTP 代理**。所以代理环境（如 Clash TUN）下 DHT 必然失败——
> 这决定了它只能是"尽力而为的补充"：三者都失败时明确报错，绝不静默卡住。
> 不想等这 2~10 秒 UDP 探测，可用 `--no-dht` 直接跳过。

**三个容易被忽略的正确性细节**（全部由测试抓出）：
1. **断点续传不能按文件大小粗判**。下载会预分配出"大小等于完整长度"的稀疏文件，按大小判断会把没下的当成下完了。正确做法：对已有数据逐分片读出并 **SHA1 校验**（`verifyExistingPieces`），坏数据会被重新下载。
2. **maxBytes 安全阀要收敛并发**。8 个 worker 会在任何分片完成之前把整批分片都派发出去，上限形同虚设；并发数被上限约束为 `ceil(maxBytes / pieceLength)`。
3. **测试必须自实现对端**。`test/helpers/fake-swarm.mjs` 用手写字节拼接（而非复用产品 bencode）构造 info 字典，并实现 tracker + 做种 peer，端到端验证「磁力 → 元数据交换 → 分片下载 → 校验 → 落盘逐字节一致」。测试助手自己曾用 UTF-8 编码二进制 peer 列表导致端口解析错乱——恰好证明了"自实现对端 + 独立编码"的验证价值。

**任务管理**（`src/download/manager.mjs`）：排队 + 并发上限、进度事件（update/progress 分离）、
取消（AbortController）、删除（可选连文件，且只删下载目录内的路径）、JSON 持久化
（进程重启后未完成任务标记为 `interrupted`；`load({autoResume:true})` 可自动重新入队续传）。

### 5.16 后端抽象：内置引擎 vs 外部客户端（qBittorrent）

内置引擎是零依赖的"够用"实现，但受限网络（代理 TUN / 机场拦 P2P）下拿不到 peer。
成熟客户端（qBittorrent）有协议加密（MSE）、更完善的 peer 策略与 DHT 实现，成功率更高。
因此下载层做了**后端抽象**：任务最终只会落在两个具体后端之一。

| 后端 | 实现 | 适用 |
| --- | --- | --- |
| `builtin` | `src/bt/engine.mjs` | 零依赖、可控、可测试；明文握手，易被 DPI 拦 |
| `qbittorrent` | `src/download/qbit.mjs`（Web API v2） | 受限网络；由 qB 负责实际下载，我们只"下单 + 跟踪 + 取消" |

`backend: 'auto'`（CLI 默认）在任务启动时探测 qBittorrent 是否可用，可用就交给它，否则回退内置引擎。
**注意区分两个常量**：`BACKENDS`（最终落地的具体后端）与 `BACKEND_CHOICES`（用户可选值，多一个 `auto`）。
早期版本混用两者，导致 `backend:'auto'` 被静默降级成 `builtin`——被测试抓到后拆开。

桥接的关键设计：

1. **字段映射要诚实**：qB 的 `size × progress` → `bytesDone`；`dlspeed` → `speed`；
   `num_seeds + num_leechs` → `peersConnected`（**已连上**的），`num_complete + num_incomplete` → `peersAvailable`（**swarm 里**的）。
   两者含义不同，不能混为一谈。
2. **状态映射要保守**：未知的 qB 状态按"下载中"处理，绝不误判成 `done`（否则会谎报完成）。
   暂停类状态映射为本项目新增的 `paused`。
3. **取消/删除语义对齐**：取消 = 从 qB 移除任务但**保留文件**（与内置引擎一致）；
   删除时 `deleteFiles` 原样透传给 qB。
4. **裸 hash 要补 tracker**：qBittorrent 只接受磁力链接，不接受 40 位裸 hash，
   所以这种情况下先补上公共 tracker 再构造磁力。
5. **凭据格式是个坑**：qBittorrent 5.x 只认 `WebUI\Password_pbkdf2`（`base64(dk):base64(salt)`）
   与 `WebUI\Password_hmac`（**HMAC 的 key 必须是原始 salt 字节**，不是 base64 字符串）。
   用错 key 会让它校验失败并**静默禁用 WebUI**，日志只写一句"未设置凭据"。
   手写配置容易踩坑（实测 5 种格式组合都失败），建议直接在 qB 的 GUI 里开启 Web UI。

### 5.17 容器部署：不是万能药，但有两个真实场景

先说结论：**容器化解决不了"网络拦截 P2P"**。Windows 上 Docker Desktop 跑在 WSL2 虚拟机里，
容器流量仍经宿主机网络栈出去，Clash TUN 照样能接管；而拦截发生在机场出口，与客户端位置无关。

容器化真正值得的两个场景：
1. **部署到 Linux NAS/服务器常驻**（跨设备访问 Web UI）；
2. **配合 VPN 容器**（`network_mode: service:gluetun`）让 BT 走一条不拦 P2P 的出口——
   这是唯一能"用容器解决封锁"的用法。

为此代码层做了**环境感知的默认值**（`src/env.mjs`），因为同一份代码在本机与容器里的合理默认值不同：

| 默认值 | 本机 | 容器 | 为什么 |
| --- | --- | --- | --- |
| 监听地址 | `127.0.0.1` | `0.0.0.0` | 容器里绑回环的话端口映射进不来 |
| qBittorrent 地址 | `127.0.0.1:8080` | `host.docker.internal:8080` | 容器里的 127.0.0.1 指向容器自己 |
| 下载目录 | `~/Downloads/...` | `/downloads`（挂卷） | 否则文件留在容器里，删容器就没了 |

容器检测按可靠性排序：显式环境变量（`TORRENT_SEARCH_CONTAINER`，也用于测试注入）→ `/.dockerenv`
→ `/proc/1/cgroup` 关键字。另外**网络诊断在容器里必须说"看不到宿主机"**，而不是因为看不到 TUN
网卡就报告"环境正常"——这类误报比不报更糟。所有默认值都可用 `TORRENT_SEARCH_*` 环境变量覆盖。

## 6. 接口契约

### 6.1 CLI

```
magnet-search <关键词> [选项]      # 聚合搜索
magnet-search serve [选项]         # 启动本地 Web UI + API（默认 127.0.0.1:8787）
magnet-search sources              # 列出数据源
magnet-search check [关键词]       # 逐源连通性自检
```

常用选项：`-s/--sources`、`--sort`、`-n/--page-size`、`--page`、`--json`、`--magnet`、
`--timeout`、`--proxy`、`--demo`、`--no-color`、`-v/--verbose`。
退出码：`0` 成功（含无结果）、`1` 运行出错或**全部**数据源失败、`2` 参数错误。

### 6.2 JSON API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/search?q=&sources=&sort=&page=&pageSize=&timeoutMs=` | 聚合搜索 |
| GET | `/api/sources` | 数据源列表 |
| GET | `/api/health` | 健康检查（版本、运行时长、Node 版本、代理） |
| GET | `/`、`/app.js`、`/style.css` | Web UI 静态资源 |

成功响应结构见 `README.md`；错误统一为 `{"error":{"code":"...","message":"..."}}`，
错误码：`bad_request` / `method_not_allowed` / `not_found` / `search_failed` / `internal_error`。

## 9. 风险与限制

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 站点改版/下线 | 对应源解析失败 | 失败被隔离并如实展示；`npm run smoke` 第一时间发现；夹具可一键重抓 |
| 地域网络限制 | 部分源连不上 | `--proxy auto` / `--proxy <url>`；`check` 命令定位到具体源 |
| 源不提供做种数/体积（dmhy） | 无法按热度判断 | 字段保持 `null` 并显示为 `-`，不伪造数据；用「来源/时间」辅助判断 |
| 版权与合规 | 法律风险 | 只聚合公开索引元数据，不托管、不缓存、不分发内容；请遵守当地法律与站点条款，仅作个人检索用途 |
| 成人内容 | 可能出现在综合源结果中 | 当前**不做**内容过滤（避免引入审核策略）；如需过滤可在适配器层加关键词黑名单 |

## 10. 后续可扩展方向

1. **更多源**：只要实现 `search(query, ctx)` 并注册进 `src/sources/index.mjs` 即可（当前架构新增一个源约 60 行）。
2. **结果本地持久化**：把历史结果落 SQLite，支持离线检索与「新资源提醒」。
3. **种子文件解析**：`src/xml.mjs` 的解析思路可复用到 bencode（`.torrent` 解析、文件列表预览）。
4. **做种数补全**：对无做种数据的源，通过 DHT/Tracker scrape 补全（会显著增加复杂度，需评估）。
5. **Web UI 增强**：结果收藏、按体积/时间区间筛选、多关键词组合语法。
